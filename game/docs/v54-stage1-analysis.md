# Version 54 第1工程:現状の分析(人物の作り方・描画の負荷・メモリの増加)

調べた環境は、開発環境の Chromium と SwiftShader(GPUを使わない、ソフトウェア描画)です。実機ではありません。

## 1. Version 53 の人物の作り方

| 項目 | Version 53 の作り方 |
|---|---|
| 顔の形 | 球(`SphereGeometry`、横16×縦12の分割)が一つだけ。頂点は約220、三角形は約360 |
| 目・鼻・口・耳 | 形はない。顔の球に貼った絵(キャンバスで描いた2D)の線だけ。耳もない |
| 肌の材質 | `MeshLambertMaterial`(光沢のない、いちばん簡単な陰影)。PBR ではない |
| 顔の絵 | あり。表情ごとに、128×128 のキャンバスに目・眉・口の線を描いて、球に貼る |
| 髪の形 | 球の一部を組み合わせたもの(後ろ・頭頂・まげの球) |
| 表情 | 顔の絵を描き替えるだけ。顔の形は変わらない(モーフ・ボーンなし) |
| 人ごとの違い | 顔立ちは3種類の線の描き方だけ。輪郭・鼻・唇の形は全員同じ |
| 体 | 円柱・回転体・箱・球を、手作りの骨組み(Group)で動かす。スキニングなし |
| 読み込み | ファイルを読まず、コードの中で形を作る |
| 人物1人の重さ | 細部ありで約30〜33の描画単位。三角形は約2,000〜3,000 |

**結論**:この作り方は、球を細かく分割しても、添付画像のような顔には近づきません。目の窪み・まぶた・鼻・唇・頬骨の形を、そもそも持っていないためです。顔の形そのものを持つメッシュを使う方式に変える必要があります。

## 2. 描画の負荷(ソフトウェア描画)

| 画質 | 平均FPS | 描画の回数 | 三角形 |
|---|---|---|---|
| 低 | 8.2 | 95 | 16.2k |
| 中 | 4.5 | 567 | 68.9k |
| 高 | 3.5 | 581 | 69.5k |

切り分けた結果は次のとおりです。

- 一コマの JavaScript は 5ms 未満です。人物の動きの計算は 0.1ms です。ここは原因ではありません。
- 描画の命令を出す処理(`renderer.render`)も、1回 1.4〜2ms でした。
- 遅いのは、SwiftShader が画面の点を塗る処理です。
  - 模様の絵を貼った大きな面(地面・床・屋根)を隠すと、9.2 → 16 FPS になりました。
  - 模様の絵をはがして色だけにすると、8.4 → 10.4 FPS でした。
- 人物を全員隠しても、FPS はほとんど変わりませんでした。人物は、描画の約38回分です。
- GPU のある実機では、点を塗る処理はずっと速くなります。そのため、ソフトウェア描画の FPS で実機の速さを決めることはできません。

これを受けて、顔の高品質化は次の設計にします。
- 近くの人(数メートル以内)だけ、高品質の顔にします。
- 遠くの人は、いまの簡単な形のままにします。
- 顔の形と絵は、全員で共有します。

## 3. 20年の進行でメモリが増えた原因

### 調べ方
1. 同じページで20年を2回進め(合計40年)、5年ごとに、ごみ集めを2回してから測りました。
2. ヒープの記録(heap snapshot)を、1年目と4年目で比べました。
3. 増えた文字列が、何から参照されているかをたどりました。
4. ヒープのサンプリングで、どこで作られたかを調べました。

### わかったこと
- セーブデータは、20年で 86KB → 446KB に増えました。これは、正常なゲームデータの増加です。
  - 人物は 226 → 255 人に増えました。記録には上限があり、戦略の記録は400件で止まります。
- メモリ(ごみ集めのあと)は、178MB → 506MB に増えました。1年に約16〜19MB です。セーブデータの増加より、はるかに大きい量です。
- 増えたもの(1年目と4年目の差):文字列 約70万個(13.8MB)、Object 約30万個(9MB)、ArrayBuffer 12.5MB。
- 文字列をたどると、どれも**オートセーブのために作ったセーブの写し**の一部でした(placement.homes など)。保存の非同期処理(`put` の `record`)が、写しを持ったまま待っていました。IDBTransaction も 84 件残っていました。
- 書き込みの数を数えると、次のとおりでした。時を早く進めたとき、オートセーブ(10日ごと・会戦のあと)を始める速さが、書き込みが終わる速さ(この環境で1件 約0.5秒)を上回り、待ちの列が伸びていました。待っている写しの分だけ、メモリが増えていました。

  | 時点 | 始めた数 | 終わった数 |
  |---|---|---|
  | 12か月分進めた直後 | 36 | 4 |
  | 5秒後 | 36 | 17 |
  | 20秒後 | 36 | 36 |

- 区別すると、次のとおりです。
  - 正常なゲームデータの増加:あり。小さい(セーブで 360KB)
  - 会話の記録・出来事の記録:上限で止まっている(会話 50件、記憶 30件、事件 60件、戦略の記録 400件)
  - Geometry・Material・Texture の解放漏れ:なし(形の数は 430〜720 を上下するだけで、増え続けない)
  - **参照が残ったもの:オートセーブの書き込み待ちの写し(これが原因)**
  - セーブの肥大:なし(20年で 446KB)

### 直したこと
- オートセーブの書き込みは、一度に一つだけにしました。書いている途中に次の保存が来たら、終わったあとで、最新の状態を一度だけ書きます。

### 直したあとの結果(同じ条件で40年、ごみ集めのあと)

| 時点 | メモリ | セーブ |
|---|---|---|
| 317年(開始) | 178MB | 86KB |
| 322年 | 187MB | 325KB |
| 327年 | 201MB | 374KB |
| 332年 | 189MB | 417KB |
| 337年(20年) | 190MB | 446KB |
| 342年 | 190MB | 464KB |
| 347年 | 191MB | 495KB |
| 352年 | 203MB | 500KB |
| 357年(40年) | 192MB | 510KB |

メモリは、190MB 前後で止まりました。軍団の作戦の記録(armyOpsLog)は 134 件まで増えましたが、小さい量です。

## 4. 写実的な人物を作るために使える資源(調べた結果)

| 資源 | 使えるか | 中身・ライセンス |
|---|---|---|
| MakeHuman(github.com/makehumancommunity/makehuman) | **使える**(git で取得できた) | 基本の人体メッシュ(約1万3千頂点。まぶた・唇・鼻孔・耳の形を持つ)、体形・顔の変形の素(数百種。アジア系・女性・年齢・鼻・頬・顎・目・口)、表情の変形(アジア系)、高精細の眼球と虹彩の絵、骨格と重み。**素材は CC0 1.0**(誰でも自由に使える)。出力物にも制限なし |
| MPFB2(MakeHuman の Blender 用) | 取得できた | 眉の変形の素、肌の質感の絵(sss.png)など |
| MakeHuman の肌・髪・眉・まつげの素材集 | **取得できない**(認証が要る、またはサイトにつながらない) | — |
| three.js の見本のモデル(LeePerrySmith の頭) | 取得できた | 男性の頭のスキャン。CC BY 3.0。後宮の女性には合わない |
| Blender の本体 | 使えない(download.blender.org につながらない) | Python 用の bpy は PyPI にあるが、試していない |
| Sketchfab・Poly Haven など | つながらない | — |
| 画像生成・3D生成の有料サービス | 使っていない(課金しない) | — |

**方針**:MakeHuman(CC0)の頭と顔のメッシュを、Python で GLB に書き出します。
- 表情:MakeHuman の表情の変形を、モーフターゲットにします。
- 人ごとの顔:顔の変形の素をモーフターゲットにして、人ごとに量を変えます。
- 肌・眉・まつげ・髪:素材集がないため、自分で作ります。
  - 肌の色と眉は、絵として描きます。
  - まつげと髪は、メッシュとして作ります。
- 体:いまの衣装の体に、新しい頭をつなぎます。
