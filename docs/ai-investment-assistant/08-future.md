# 8. 将来の拡張方針

**この章で決めること:** 将来どんな機能を足せるか、そのために今どんな作りにしておくか。

---

## 8.1 拡張しやすくするための設計上の工夫(最初から入れておくもの)

| 工夫 | 効果 |
|---|---|
| 計算(`domain/`)を画面・DBから分離 | 計算ロジックの再利用・テストが容易。将来Pythonへ移すことも可能 |
| 外部API(`providers/`)を共通インターフェース化 | APIの乗り換え・追加が1ファイルで済む |
| 資産クラス・口座区分を固定のコードではなく値で管理 | 新しい資産種類(仮想通貨・債券など)を追加しやすい |
| AI分析の入出力を JSON Schema で定義し `prompt_version` を記録 | プロンプト改良の効果を比較できる。モデル変更も容易 |
| 計算結果に `calc_version` を記録 | 計算ロジックを直したとき、いつの値がどの方法で計算されたか追跡できる |
| 取引履歴を唯一の正データにする | 過去にさかのぼって再計算できる |

## 8.2 拡張候補

| 分類 | 内容 | 想定時期 |
|---|---|---|
| 資産 | 仮想通貨(取引所APIの読み取り専用キー)、債券、金、iDeCo の詳細 | 中期 |
| 資産 | 家計簿・収支との連携(毎月の積立余力の自動計算) | 中期 |
| データ | 日本株の場中株価(有料データの導入) | 必要に応じて |
| データ | 有価証券報告書(EDINET / SEC)の自動要約・前年との差分 | 中期 |
| 分析 | Python サービス(FastAPI)の追加: バックテスト、相関分析、効率的フロンティア、モンテカルロ・シミュレーション | 中期 |
| 分析 | リバランス提案(目標配分との差から、売買すべき金額を計算) | 中期 |
| 分析 | ストレステスト(「円高10%」「金利+1%」「株価−30%」時の資産額) | 中期 |
| 分析 | 決算説明資料・決算短信PDFのAI読み込み | 中期 |
| AI | ポートフォリオ全体について会話できるAIエージェント(自分のDBを検索するツール付き) | 中期 |
| 通知 | LINE / メール / プッシュ通知、価格・指標アラート | Phase 7〜 |
| UI | ネイティブアプリ化(PWAで不足する場合のみ。Capacitor等) | 長期 |
| 税務 | 年間損益レポート、損出し(タックスロス・ハーベスティング)候補 | 長期 |
| 家族 | 家族の資産の閲覧共有(権限管理を追加) | 長期 |

## 8.3 将来の技術的な見直しポイント

- データ量が増えたら: Supabase Pro への移行、株価テーブルの期間分割
- 定期ジョブが複雑になったら: ジョブ専用の実行基盤(Supabase Edge Functions / GitHub Actions / Inngest など)
- 計算が重くなったら: スナップショットの事前計算、Pythonサービスへの切り出し
