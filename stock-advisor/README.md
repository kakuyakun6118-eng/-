# 株価インパクト・アドバイザー

ニュース見出しとテクニカル指標をもとに「今日のおすすめ銘柄」と「保有株の売り/継続」の参考情報を表示する、個人利用向けの Next.js アプリです。**有料APIはClaudeのみ**で、ニュース(Google News)と株価(Yahoo Finance)はキー不要です。

**これは投資助言ではありません。** 表示される判定はルールベースとLLMによる参考情報であり、正確性・妥当性を保証しません。実際の売買判断はご自身の責任で行ってください。第三者への提供・販売は金融商品取引法上の投資助言業規制の対象になり得るため想定していません。

## 構成

元の設計図(X投稿の取得 → 銘柄コード抽出 → LLM解釈 → 株価API → ダッシュボード/通知)から、このMVPでは以下を実装しています。

| 段階 | 元の設計 | このMVPでの実装 |
| --- | --- | --- |
| 情報収集 | X (Twitter) API | **Google News RSS**(無料・APIキー不要)。X APIは有料契約が必須なため採用していません(後述)。`src/lib/news.ts` の `NewsSource` インターフェースを実装すれば差し替え可能 |
| 銘柄コード抽出 | バックエンド処理 | ウォッチリスト(`data/watchlist.json`)・保有株(`data/holdings.json`)から直接ティッカーを指定する方式に簡略化 |
| 解釈・影響度判定 | Claude/OpenAI API | 2系統。`/theory` は**紫蘇の葉理論**(`src/lib/theory.ts` + `src/lib/theoryPrompt.ts`)、`/` と `/holdings` は汎用のニュース影響度判定(`src/lib/llm.ts` + `src/lib/newsPrompt.ts`) |
| 株価データ | yfinance | `yahoo-finance2`(Node製、日本株ティッカー `XXXX.T` に対応) |
| ダッシュボード | Next.js | 実装済み(`/` = おすすめ一覧、`/holdings` = 保有株管理・売り時判定) |
| 通知 | Discord/LINE | 実装済み(`POST /api/notify`)。Discordはwebhook、LINEはMessaging APIのプッシュ |

[http://localhost:3000](http://localhost:3000) が開きます。**APIキーなしでもこの時点で動きます**(株価・ニュース記事数・話題性の判定まで)。

## iPhoneでアプリとして使う

このアプリはNode.jsサーバーが必要なため、**iPhone単体では動きません。** どこかで常時動かし、iPhoneのSafariから開いて「ホーム画面に追加」する形になります。

追加するとアドレスバーのない全画面で起動し、独自アイコンが付きます(`manifest.ts` / `apple-icon.png`)。

> **iPhone上でサーバーを動かすことについて**: iSH や a-Shell といったiOS上のLinux環境は、x86エミュレーションで極端に遅く、Next.jsのビルドは現実的な時間で終わりません。またiOSは他アプリに切り替えるとバックグラウンドのプロセスを停止するため、サーバーとして機能しません。この方向は選択肢になりません。

iPhoneしか持っていない場合はこれ一択です。**必ず `APP_PASSWORD` を設定してください**(後述)。

**ファイル保存が必要なため、永続ディスク(ボリューム)を持てるホストを選びます。** 本アプリはウォッチリスト・保有株・判定履歴を `data/` 配下のJSONファイルに保存します。Vercelのようなサーバーレス環境はファイルシステムが読み取り専用(書けても実行ごとに消える)なので**そのままでは動きません**。

### キャッシュについて

1画面の表示につき「株価取得 × 銘柄数」「ニュース取得 × 銘柄数」「LLM判定 × 銘柄数」の外部呼び出しが発生するため、`src/lib/cache.ts` のTTLキャッシュを挟んでいます(株価60秒 / ニュース15分 / LLM判定30分)。LLM判定のキャッシュキーには見出し内容のハッシュを含めているので、新しいニュースが出れば自動的に再判定されます。API障害時の結果はキャッシュされません。

プロセス内メモリのキャッシュなので再起動で消えます。エントリ数は上限(既定2000件)で頭打ちにし、超えたら期限切れ→期限の近い順に捨てます。LLM判定のキーは見出しのハッシュを含むため、上限がないと際限なく増えるためです。個人利用では十分ですが、複数インスタンスで運用する場合はRedis等に差し替えてください。

### X (Twitter) API を使っていない理由

当初は特定アカウントの投稿を追跡する設計でしたが、**X APIは有料契約が必須**で、消費量も「取得した投稿数」で課金されます。試算では1回100件取得・キャッシュ10分の設定で月間約21,000件となり、Basicプラン(月15,000件程度・約$200/月)を超えていました。無料枠(月100件程度)なら1回の画面表示で使い切ります。

そのため**Xへの依存を完全に取り除きました**。現在の外部データ源は Google News と Yahoo Finance のみで、いずれもAPIキー不要・無料です。有料APIはClaudeだけです。

ルール1(話題性の急上昇)は「監視アカウントの言及数」から**「ニュース記事数」**に置き換えています。「直近24時間の件数が通常の3倍以上か」という理論の構造はそのままです。

**この置き換えで失われた機能**: 監視アカウントが言及した銘柄を自動的に候補に加える機能はなくなりました。対象銘柄は `/settings` のウォッチリストと保有株に限られます。

### アクセス制御

`src/proxy.ts` で3つのことを行っています。

1. **パスワードログイン。** `APP_PASSWORD` を設定すると、全ページ・全APIがログイン必須になります。未設定なら認証は無効のままなので、ローカル利用の挙動は変わりません。**インターネットに公開する場合は必ず設定してください。**
2. **クロスサイトからの書き込みを遮断。** ブラウザは任意のWebページから `localhost:3000` にPOSTできてしまうため、`Origin` / `Sec-Fetch-Site` が別サイトの書き込みリクエストは403で拒否します。常時有効です。
3. **cron用エンドポイントの保護。** `/api/notify` と `/api/history/record` はログインできないため、`APP_TOKEN` で認証します。`Authorization: Bearer <token>` か `X-App-Token: <token>` で送ってください。

```bash
0 9-15 * * 1-5 curl -fsS -X POST -H "Authorization: Bearer $APP_TOKEN" http://localhost:3000/api/notify
```

セッションは署名付きCookie(HMAC-SHA256、30日)で、サーバー側に状態を持たないため再起動しても維持されます。パスワードを変更すると全セッションが無効になります(避けたい場合は `SESSION_SECRET` を設定)。

### 同時実行の制御

- 銘柄ごとの情報取得(株価・ニュース・LLM)は同時 `ENRICH_CONCURRENCY` 件(既定4)までに制限しています。無制限だとウォッチリストの銘柄数だけ同時にLLMを呼び、レート制限と費用増を招くためです。
- `data/` 配下のJSONは読み取り→変更→書き込みを1つのロック内で行うため、同時追加でも取りこぼしません。書き込みは一時ファイル経由のリネームなので、途中でクラッシュしてもファイルが壊れません。

### データ取得の失敗表示

株価・ニュース・LLM の取得に失敗した場合、画面上部に赤いバナーで失敗元とエラー内容を表示します。**「材料がないから空」なのか「APIが落ちているから空」なのかを区別できるようにするため**です。直近5分以内の失敗のみ表示します。

## 使い方

- **`/`(今日のおすすめ)**: 株価変動・出来高・ニュース影響度・**紫蘇の葉理論スコア**を組み合わせたスコアで並べ替えて表示します。対象はウォッチリストと保有株の銘柄です。
- **`/holdings`(保有株)**: 銘柄コード・株数・取得単価を手入力で登録すると(`data/holdings.json` に保存)、「売り時を判定する」ボタンで現在値・含み損益・ニュース影響度・**理論スコア**を踏まえた 売却検討/様子見/継続保有 の参考情報を表示します。登録済みの株数・取得単価は行内の「編集」から変更できます。
- **`/settings`(設定)**: ウォッチリストの銘柄をブラウザ上で追加・削除・名称変更できます。銘柄コードは `7203` / `7203.T` / `【7203】` のいずれでも受け付けて正規化します。2024年以降の英数字コード(例: `130A`)にも対応しています。
- **`/theory`(紫蘇の葉理論スコア)**: 対象銘柄ごとに、3ルールの内訳(該当/非該当・配点・根拠)と判定の元になった記事一覧を表示します。

## 紫蘇の葉理論スコア

`/theory` の判定ロジックです。3つのルールの合計点(-30〜+70点)で評価します。

| ルール | 配点 | 判定方法 |
| --- | --- | --- |
| 1. 話題性の急上昇 | +30 | **実測**(`src/lib/theory.ts`)。直近24時間のニュース記事数が、その銘柄の通常時の1日あたり記事数の3倍以上か(かつ2件以上) |
| 2. ポジティブ感 | +40 | **LLM判定**(`src/lib/theoryPrompt.ts`)。「業績予想の上方修正」「新技術・新サービス」「好決算」など具体的な好材料に基づく報道か |
| 3. リスクの有無 | -30 | **LLM判定**。「過熱・煽り」「公募増資」「不祥事」などの減点要素を含むか |

**ルール1をLLMに判定させていないのは意図的です。** 記事数の増加は数えられる量なので、推測させるより実際に数えたほうが正確です。ルール2・3は文意の解釈が必要なのでLLMが担当します。

判定結果は各ルールの内訳(該当/非該当・配点・根拠)まで画面に表示されるので、なぜその点数になったかを追えます。合計点は `strong`(40点以上)/ `watch`(10点以上)/ `neutral`(0点以上)/ `caution`(マイナス)の4段階に振り分けられます。ただし**リスク(ルール3)が該当している銘柄は、合計点が高くても `strong` にはなりません**(最高でも `watch`)。理由は後述します。

### ルール1の実測に関する注意

「通常時」の基準値には2つの供給源があり、**記録済みの日次履歴があればそちらを優先**します(画面には「基準: 記録済みの日次履歴 / 取得したニュースフィード」と表示されます)。

1. **記録済みの日次履歴**(推奨): `data/history/mentions.json` に蓄積した日次記事数の平均。1回のフィード取得長に縛られないため、報道の多い銘柄でも正しい基準値が出ます。3日分以上記録されると有効になります(`MIN_HISTORY_DAYS`)。
2. **取得したニュースフィード**(フォールバック): 取得した記事(既定60件、`NEWS_FEED_SIZE`)のうち直近24時間より前の期間から算出。この期間が1日分に満たない場合は「判定不能」として0点にします(誤った基準で加点しないため)。

**倍率に加えて記事数の下限(2件)を課しています。** 報道の少ない銘柄は基準値が0.1件/日などになるため、**通常の記事が1件出ただけで「10倍」と判定されて満点が入ってしまう**ためです。1件は急上昇ではありません。

## 判定履歴と答え合わせ(`/history`)

日次で「記事数」と「判定内容+その時点の株価」を記録し、後から検証できます。

- **記録**: `/history` の「今日の判定を記録」ボタン、または `POST /api/history/record`。同じ日に複数回実行してもその日の記録を置き換えるだけです(二重計上しません)。
- **保存先**: `data/history/mentions.json`(基準値用の日次記事数)と `data/history/snapshots.json`(判定スナップショット)。個人の取引データなので `.gitignore` 済みです。
- **表示**: 過去の判定を、**分割・配当調整済み**の株価で比較した騰落率とともに一覧表示します。判定区分(有力/注目/中立/警戒)ごとの成績を、**保有期間を揃えて**(翌営業日 / 5営業日後 / 20営業日後)集計します。

**調整済み株価を使う理由**: 生の株価で比較すると、1:3の株式分割があった銘柄は全ての過去判定が -67% と表示されてしまいます。Yahoo の `adjclose`(分割・配当調整済み終値)を使うことでこれを避けています。

**保有期間を揃える理由**: 1日前の判定と3か月前の判定を同じ「平均リターン」に混ぜても、理論が機能しているかは分かりません。各判定を同じ営業日数で測ることで比較可能にしています。保有期間が未経過の判定は、その期間の集計から除外されます(件数は括弧内に表示)。

日次のcron設定例:

```bash
# 毎営業日 15:30 JST(大引け後)に記録
30 15 * * 1-5 curl -fsS -X POST -H "Authorization: Bearer $APP_TOKEN" http://localhost:3000/api/history/record
```

日付は**JST基準**で区切ります(日本市場のため、UTC深夜の記録が前日扱いにならないようにしています)。

記録が飛んだ日は単に欠測として扱い、平均は「記録された日数」で割ります(観測していない日について推測しないため)。

**注意**: 区分ごとの勝率はサンプル数が少ないうちは偶然に大きく左右されます。数件の実績で理論の有効性を判断しないでください。

### スコアの反映先

理論スコアは `/theory` の表示だけでなく、他の2画面の判定にも入ります。

**`/`(今日のおすすめ)**: 理論スコアがある銘柄は、重みを ニュース0.4 / テクニカル0.25 / 理論0.35 に組み替えて総合スコアを算出します。理論スコアは -30〜+70 を -100〜+100 に正規化して合成します。

**`/holdings`(保有株)**: 以下のルールを既存の損益ベース判定より優先します。

| 理論スコアの内容 | 判定 |
| --- | --- |
| 公募増資・不祥事 | **売却検討**(含み益が出ていても優先) |
| 過熱・煽りのみ | **様子見**(売りシグナルとは扱わないが過熱に注意) |
| 好材料あり(合計プラス) | 含み損・含み益による売却/利確判定を保留し**継続保有** |

**過熱・煽りは点数に埋めず、警告として別枠で表示します。** 総合スコアだけ見ると理由が分からなくなるため、`/` のカードに「材料の実体より人気が先行している可能性があり、急落に注意」と明示します。

### 配点40点の曖昧さへの対処

合計40点になるケースは2通りあります。

| 内訳 | 合計 | 実態 |
| --- | --- | --- |
| 話題性 +30 / 好材料 +40 / リスク -30 | 40点 | 煽りを伴う急騰銘柄 |
| 話題性 0 / 好材料 +40 / リスク 0 | 40点 | 地味だが好材料のある銘柄 |

同じ点数でも性質が正反対なため、**リスクが該当している間は `strong`(有力)にしない**ようにしています(`verdictFor()`)。上の例では前者が `watch`(注目)、後者が `strong`(有力)になります。煽り・公募増資・不祥事を抱えた銘柄が「有力」として提示されることはありません。

## 通知(Discord / LINE)

`POST /api/notify` で、判定結果のうち**割り込む価値のあるものだけ**を通知します。

### 通知する条件

| 条件 | 種別 | 理由 |
| --- | --- | --- |
| 保有株に「公募増資」「不祥事」の報道 | 警告 | 保有中の銘柄に対する具体的な悪材料。最優先 |
| 保有株が売却検討シグナル | 警告 | 既に持っている以上、行動が必要 |
| 紫蘇の葉理論で有力(40点以上) | 情報 | 新規候補 |

**「過熱・煽り」だけの銘柄は通知しません。** 煽りは理論が減点対象としているノイズそのものなので、わざわざ割り込む理由がありません(ただし画面上には警告として表示されます)。保有株の警告は新規推奨より前に並べます。通知本文には必ず免責文を付けます。

### 設定

`.env.local` に設定したチャネルにだけ送信します(未設定のチャネルはスキップ)。

```bash
# Discord: サーバー設定 → 連携サービス → ウェブフック → URLをコピー
DISCORD_WEBHOOK_URL=

# LINE: Messaging APIのチャネルアクセストークンと宛先ユーザーID
LINE_CHANNEL_ACCESS_TOKEN=
LINE_TO=
```

**LINE Notify は2025年3月31日でサービス終了しているため使えません。** LINE Developers コンソールで Messaging API チャネルを作成してください。

### cron設定例

```bash
# 平日9:00〜15:00の毎時0分に判定して通知
0 9-15 * * 1-5 curl -fsS -X POST -H "Authorization: Bearer $APP_TOKEN" http://localhost:3000/api/notify
```

(`APP_TOKEN` 未設定ならヘッダは不要です)

同じ条件は**24時間のクールダウン**を挟むため、毎時実行しても同じ警告が繰り返し飛ぶことはありません。条件が翌日も続いていれば1日1回だけ再通知されます。送信済みの記録は `data/history/notified.json`(gitignore済み)に保存します。

**全チャネルの送信に失敗した場合はクールダウンを開始しません。** 通知先の障害で警告が握りつぶされるのを防ぐためです。

送信せずに内容だけ確認したい場合:

```bash
curl -X POST 'http://localhost:3000/api/notify?dryRun=1'
```

## 制約・既知の限界

- 紫蘇の葉理論のルール1(話題性)は、日次記録が3日分溜まるまではニュースフィード(既定60件)から基準値を算出します。報道の多い銘柄では数日分にしかならないため、運用初期は `/history` で日次記録を貯めてください。
- 通知・履歴記録はいずれもプロセス外からの定期実行(cron等)が前提です。アプリを起動しているだけでは自動送信されません。
- **`APP_PASSWORD` を設定しない限り、ブラウザUIには認証がかかりません。** ローカル利用では不要ですが、インターネットに公開する場合は必須です。
- `data/holdings.json` は保有銘柄・株数・取得単価を含む個人の金融情報のため `.gitignore` 済みです(雛形は `data/holdings.example.json`)。ウォッチリストは初期設定として引き続きGit管理下にあります。
- 保有株・ウォッチリストはローカルJSONファイルに保存されます(`/settings` と `/holdings` から編集可能)(認証や複数ユーザー対応はありません)。個人利用を前提としています。
